# Fix: Total Spend shows $111K but Replit Settings → Usage shows $107K

## Background (read first)

The dashboard headline is the "account anchor": a SUM of stored daily chunks
(synchronizeUsage("account_total") → aggregateAccountUsage sums per-chunk
totalCostUsd), NOT one live /usage call. Two ways it can drift high:

1. Chunks older than the 7-day reconciliation window (RECONCILIATION_OVERLAP_MS)
   keep values Replit has since restated DOWNWARD (corrections, de-duplicated
   double-metered entries). The live API always returns the latest values; our
   stored chunks don't.
2. The headline window is still hardcoded 2026-05-20 → now, while Settings →
   Usage shows billingPeriod=current. If the real period starts after May 20,
   we include spend Settings doesn't.

## Step 0 — Diagnose before changing any code

Make ONE raw unfiltered call for the app's exact window:

GET https://api.replit.com/v1/usage?startTime=2026-05-20T00:00:00.000Z&endTime=<now ISO>
(Authorization: Bearer REPLIT_ENTERPRISE_API_KEY)

Compare data.totalCostUsd to the dashboard headline ($111K):
- If the raw call returns ≈ $107K → stale chunks confirmed. Run
  POST /api/usage/ranges/rebuild for the billing range and verify the headline
  drops to match. Then implement ALL THREE tasks below.
- If the raw call returns ≈ $111K → window mismatch confirmed. Check
  /api/status → billingPeriod fields / differsFromReportingCutoff. Task 2 is
  the fix; still implement Tasks 1 and 3.

Report which case you found, with the actual numbers, before proceeding.

## Task 1 — Self-healing account anchor

Add a daily job (also run once on server start after cache hydration):
fetch the full billing range in ONE unfiltered /usage call (no groupBy, no
pagination needed) and compare totalCostUsd against the chunk sum from
aggregateAccountUsage for the same rangeKey. If they differ by more than $1,
log the delta and automatically trigger the existing atomic rebuild
(rebuildUsageRangeAtomically) for the account_total scope of that range.
Surface last-verified time + last delta on /api/status and the Settings page.
One extra API call per day is negligible against the 100/min rate limit.

Accept when: manually corrupting a stored chunk value (test env) is detected
and healed on the next verification pass, and /api/status shows the
verification timestamp + delta.

## Task 2 — Headline window follows the verified billing period

The T7 job already fetches the real billing period (billingPeriod=current
interval) and computes differsFromReportingCutoff. When the verified period
start is AFTER the 2026-05-20 cutoff, make the default "billing" range use the
verified period bounds instead of the cutoff (keep the cutoff as a floor for
periods starting before data existed). Show a visible banner when the windows
differ. Also fix the existing label/data mismatch: the headline card's
description currently shows the real billing-period label while the number
covers cutoff → now.

Accept when: the headline card's number and label describe the same date
window, that window matches the in-product usage page default, and the banner
appears only when the windows genuinely differ.

## Task 3 — Sync hygiene

1. Delete the dead fullRebuild=true branch inside synchronizeUsage: it resets
   `previous` to undefined and re-inserts a bootstrap chunk while the DELETE
   only clears rows inside the recent window — if ever called it would
   double-cover everything before the 7-day overlap. The safe path is
   rebuildUsageRangeAtomically (deletes the whole rangeKey first); keep only
   that.
2. In isDurablyFresh, stop treating failed/partial sync scopes as fresh: a
   failed account_total sync currently freezes a stale headline until a manual
   retry. Make failures eligible for automatic re-queue with backoff.

Accept when: a unit test asserts stored chunk intervals never overlap for any
synchronizeUsage caller, and a simulated failed anchor sync retries
automatically instead of serving stale data indefinitely.

## Critical requirement

Do not mark this complete because code changed. Verify the rendered dashboard
headline equals the raw unfiltered /usage totalCostUsd for the same window
(within ingestion lag), and state both numbers in your final report.
