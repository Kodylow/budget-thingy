# Handoff: Budget Monitor performance and correctness rebuild

## Summary

The dashboard is slow because it fetches usage from the Enterprise API on
demand, keys its cache by date range, and blocks requests on those fetches.
Its numbers also drift from the Enterprise API's own totals. This document
lists the causes with file references, a nine-step plan to fix them, and
acceptance criteria for each step.

## Evidence from the `db.sql` snapshot

- `usage_sync_chunks`: 42,492 rows / 17.6 MB, all loaded into RAM at boot.
- `usage_sync_state`: 14,046 rows across 509 distinct range keys.
- The default "full term" view produced a new ~380-scope cold start on each of
  08-28, 08-31, 09-01, 09-02, because the cache key includes today's date.
- Trends created 27 distinct 7-day windows at ~380 scopes each (~10K scopes).
- Billing-period discovery flapped three times in one week (Aug 1–Sep 1,
  Aug 19–Sep 19, Sep 1–Oct 1). Each flip invalidated every `billing:` and
  `pace:` scope.
- 5,644 sync states completed on 2026-08-27 alone.
- `api_account_total_verification`: upstream $12,879 vs stored $6,605
  (delta $6,274, outcome `healed`). The attributed total was 49% below the
  source of truth before the heal path overwrote it.

With 179 custom groups and 20 workspaces, a cold default view needs roughly
3,000–4,500 `/usage` calls through a serial queue with a 700 ms sleep per
task: about 50 minutes of pacing before network latency or pagination.

## Root causes

Paths are under `artifacts/api-server/src/` unless noted.

1. **Cache key changes daily.** `lib/enterprise.ts:145` builds
   `custom:<start>:<endDate>`.
   `artifacts/budget-monitor/src/lib/range-selection.ts` sets the end date to
   the browser-local today, so the key also differs by user timezone.
   `planSyncChunks` (`lib/enterprise.ts:624`) issues 1 historical + 7 daily
   chunks per cold scope. Prune (`lib/enterprise.ts:541`) only removes
   *closed* custom states; an abandoned rolling key never gets the later
   refresh that would close it, so those rows accumulate forever.

2. **One serial queue for everything.** `lib/enterprise.ts:196-240`.
   Interactive loads, trends, project metadata, group totals, the alert
   checker, snapshots, and billing-period refresh share one array and one
   runner. Flat 700 ms sleep after every task (`:221`) and between chunks
   (`:853`). A running task (up to 8 chunks × 200 pages × 31 cursorless
   shards) cannot be preempted; priority (`:232`) only reorders unstarted
   tasks. Pacing ignores the `X-RateLimit-*` headers except to pause when
   remaining ≤ 3 (`:456`).

3. **Directory refresh blocks all callers.** `getDirectory`
   (`lib/enterprise.ts:1779`) awaits ~212 sequential paginated calls
   (1 workspaces + 20 group lists + 179 group-member lists + members + budgets)
   once the 15-minute TTL expires. `lib/authz.ts` calls it for authorization,
   so login and every API request stall for the whole rebuild. `rawFetch`
   (`:44`) has no timeout, so one hung upstream call hangs the app.

4. **Checker forces a full re-sync every 10 minutes.** `lib/checker.ts:564`
   runs `runCheck(true)`. `force` zeroes `completedAt`
   (`lib/enterprise.ts:826`), defeating the TTL for 179 groups × 3 modes plus
   all workspaces. It then waits up to 5 minutes for raw spend
   (`checker.ts:450`) behind the project fetches it queued first
   (`checker.ts:402`). Deferred runs still stamp `lastCheckAt` (`:501`), so
   the UI says "checked" when nothing was evaluated. `markUsageSyncQueued`
   (`lib/enterprise.ts:1115`) keeps a stale scope marked `success` while its
   forced replacement is queued, so alerts evaluate old data as complete.
   The warm-up (`checker.ts:540`) warms the `billing` range, never the
   `full-term` range the dashboard actually opens with.

5. **Upstream I/O inside a Postgres transaction.** `synchronizeUsage`
   (`lib/enterprise.ts:804-923`) takes `pg_advisory_xact_lock`, then performs
   every fetch before writing. One pooled connection is pinned for minutes per
   scope. Every autoscale replica also starts its own checker, snapshot job,
   and team-budget sync (`index.ts:29-38`), so N replicas queue N copies of
   the same work and block on each other's locks.

6. **Boot hydrates everything.** `initCache` (`lib/enterprise.ts:1521`)
   selects all of `usage_sync_state` and `usage_sync_chunks`, aggregates every
   chunk in JS, then does a live `refreshBillingPeriodMetadata(0, true)`
   before Express listens. `prestart` runs `drizzle-kit push` on every start.
   Autoscale scale-up is slow and each replica repeats it.

7. **Aggregation is per-request and quadratic.** `getCanonicalUsage`
   (`lib/enterprise.ts:3606-3901`) runs on every 8-second `/groups` poll,
   again for `paceRange`, and again in `/summary`. Inside it:
   `remainingGroupCapacity` (`:3672`) reduces a map on every call and is
   called per user (`:3729`, `:3759`); `workspaceGroups.find(... includes(userId))`
   (`:3694-3697`, `:3707`) is O(users × groups × members);
   `orderedGroups.find` (`:3736`) runs inside a loop. `/groups`
   (`routes/monitor.ts:423-487`) then calls `getFiredThresholds` once per
   display group inside `Promise.all`: 179 queries per poll.

8. **Billing view doubles the work.** `routes/monitor.ts:341-349` queues the
   entire scope set a second time for `paceRange`. `pace:` replaces its whole
   interval on every refresh (`lib/enterprise.ts:649`).

9. **Frontend amplifies server churn.**
   `artifacts/budget-monitor/src/pages/group-detail.tsx:38-52` calls
   `removeQueries` on unmount, so returning to the dashboard is always a cold
   fetch. `App.tsx:23` uses a default `QueryClient` (`staleTime: 0`, refetch
   on focus). Trends poll every 3 s with no terminal state for partial or
   failed components (`pages/trends-tab.tsx:387`). One 989 KB JS chunk, all
   routes eager, no table virtualization.

## Target architecture

Separate the three concerns `lib/enterprise.ts` currently fuses:

- **Ingestion**: background only, paced by live rate-limit headers,
  claim-protected across replicas, fixed cadence independent of traffic.
- **Storage**: normalized daily rows; prior months immutable.
- **Serving**: read Postgres, return immediately, label data age and
  staleness.

## Work plan

Ship each step as its own PR. Steps 1–5 remove most of the pain; 6–9 make it
durable. Keep the existing sync path behind a flag until Step 1 is verified
against the account-total check.

### Step 1: Daily fact table with stable identities

- Add `usage_daily(entity_type, entity_id, workspace_id, scope_key, date,
  cost_usd, ai_cost_usd, fetched_at)`. PK
  `(entity_type, entity_id, scope_key, date)`; index `(entity_type, date)`.
  `entity_type` ∈ `account | workspace_member | group_member | group_project |
  group_total`.
- Ingest by UTC month. A prior month becomes final 24 h after it ends and is
  never fetched again. Only the current month is mutable.
- Every range (full term, MTD, billing, custom, trends bucket) becomes
  `SUM(cost_usd) WHERE date BETWEEN` over `usage_daily`. Remove range-keyed
  identity from the read path.
- Compute all dates server-side in UTC. Never use a browser-local date as
  cache identity.
- Backfill from `usage_sync_chunks`: daily chunks map 1:1 to rows; historical
  bootstrap chunks need one re-fetch per month (use `groupBy=date` if the API
  supports it; otherwise one call per month per scope).
- Acceptance: default view served with zero upstream calls; `/groups` p95
  under 500 ms with warm Postgres; account-total verification delta under $1.

### Step 2: Serve stale, never block

- `getDirectory`: return any cached copy immediately; start one background
  refresh; expose `directoryFetchedAt` in responses. Authorization must never
  wait on upstream.
- Replace the "cold scope blocks UI" rule in `markUsageSyncQueued` and
  `getUsageSyncSummary`: return whatever rows exist, set `isStale` and
  `dataAsOf`, and report `syncing` only for a scope with no rows at all.
- `rawFetch`: pass `signal: AbortSignal.timeout(30_000)`.
- Acceptance: no HTTP request handler awaits an Enterprise API call.

### Step 3: Workload classes with a real budget

- Read `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` on
  every response into a token bucket.
- Three classes: interactive (30% of the limit reserved), scheduled refresh
  (≤50%), backfill (remainder). Separate workers per class; interactive
  concurrency 2–3, background 1.
- Remove the flat 700 ms sleeps; pace from the bucket.
- Acceptance: an interactive request never waits behind a running background
  task; observed request rate stays under the header-reported limit.

### Step 4: Cheap, honest checker

- Remove `force=true` from the scheduled run. The checker reads `usage_daily`
  and compares to budgets; it does no fetching.
- Record `evaluatedDataAsOf` on every alert. Do not update `lastCheckAt` when
  evaluation was skipped; expose `lastEvaluatedAt` and `lastSkippedReason`.
- Acceptance: checker completes in under 1 s; every alert row carries data
  age.

### Step 5: One scheduler with cross-replica claims

- Guard refresh, snapshot, team-budget sync, and checker with a Postgres
  claim: `INSERT INTO job_claims ... ON CONFLICT DO UPDATE ... WHERE
  claimed_at < now() - ttl RETURNING`. The winner runs; others skip.
- Cadence: every 5 min refresh current-month `workspace_member` for all
  workspaces first (20 calls), then group member/project scopes round-robin
  under the background budget.
- Acceptance: upstream call volume is constant regardless of open dashboards
  or replica count.

### Step 6: Network calls out of the transaction

- Fetch outside the transaction. Open a short transaction for
  `DELETE ... WHERE date >= replacementStart` plus one multi-row insert
  (`jsonb_to_recordset` or batched `VALUES`). Hold the advisory lock only
  around the write.
- Set explicit `pg.Pool` `max`, `idleTimeoutMillis`, and `statement_timeout`.

### Step 7: Precomputed canonical rollup

- Materialize attribution into `canonical_group_user_spend(month, group_id,
  user_id, ai_usd, non_ai_usd, residual_usd)` when new rows land. `/groups`,
  `/summary`, group detail, exports, and the checker all read this table.
- In `getCanonicalUsage`: build `Set`s for `groupMembers` once; keep a running
  `attributedTotalByGroup` map instead of reducing per user; index groups by
  id. This alone turns the function from quadratic to linear.
- Batch `getFiredThresholds` into one `WHERE group_id = ANY($1)` query.

### Step 8: Fast boot

- Remove full chunk hydration from `initCache`; read `usage_daily` on demand
  with a small in-process LRU.
- Move `drizzle-kit push` out of `prestart` into a deploy step.
- Do not await `refreshBillingPeriodMetadata` before listen.
- Persist the billing-period anchor and switch only when the upstream
  interval is identical across two consecutive observations.

### Step 9: Frontend

- `QueryClient` defaults: `staleTime: 60_000`, `refetchOnWindowFocus: false`.
- Replace `removeQueries` on group-detail unmount with `invalidateQueries`.
- Trends polling: terminal state on partial/failed; back off 3 s → 8 s → 30 s.
- `React.lazy` for settings, directory, trends, admin, and user guide routes.
- Virtualize group and member tables with `@tanstack/react-virtual`.

## Expected results (179 groups, 20 workspaces)

| Metric | Now | After steps 1–5 |
|---|---|---|
| Cold default-view upstream calls | ~3,000–4,500 per day | 0 interactive; constant background |
| Time to first data after auth | seconds to tens of minutes | under 500 ms |
| Checker duration | over 10 min, often deferred | under 1 s |
| Per-poll server work | 2–3 quadratic rollups + 179 queries | 1 indexed read |
| Replica boot | 17.6 MB JSON + live API call + schema push | immediate listen |
| Cache storage | 42K chunks, unbounded | one daily table, prunable by date |

## Rules for this work

- Every PR must keep the `api_account_total_verification` delta under $1 for
  the current month. If `usage_daily` disagrees with the upstream account
  total, the PR is not done.
- Once `usage_daily` serves reads, delete the range-keyed machinery
  (`planSyncChunks`, `syncMetadata`, `getUsageSyncSummary`, closure/grace
  logic, custom-range pruning) instead of tuning it.
- Do not add new sync scopes keyed by a moving date.
- Do not add polling intervals under 8 s.
- Do not add background jobs without a cross-replica claim.
